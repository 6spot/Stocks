# Stocks 分阶段交付路线图

## 目标与用户价值

依据已有设计拆分成可独立验收的 Trellis 交付任务，优先完成真实研究闭环，再建设可靠日常运行与研究深化；本轮只规划，不开始产品实现。

## 背景与依据

阶段已由 `docs/architecture.md:7` 和 `docs/validation.md` 定义；当前实现见[代码现状](research/baseline.md)。已有模型、S3 helper、chat client 和文档列表不算采集/研究已实现。现有用户未提交的设计改动是本次规划依据，保持原样。

## 要求

- R1：严格使用 V0 / V1 / V2 范围，不把安全、原件、版本、引用及 pgvector 底线推迟。
- R2：路线图 → 阶段父任务 → 独立交付子任务；每个子任务有目标、排除项、依赖、可观察验收与最小验证计划。
- R3：父子归属和依赖分开记录；每项依赖同时写入任务文档和 `meta.depends_on`，不误称 Trellis 自动调度。
- R4：不做旧库迁移、旧版兼容或无关平台化；领域契约继续由现有 docs 唯一维护。
- R5（初始规划约束）：当时保持 planning、不激活任务、不编辑产品代码，不把计划验证说成已通过。后续实际交付与 2026-10-27 收尾分别记录，不用历史约束否认已授权实施/归档。
- R6（2026-10-27 收尾）：按 [Owner 最终范围决定](final-acceptance-scope.md) 收敛六项验收，保留未知费用、真实证据边界与未修复问题；授权父任务归档不等于全部端到端场景通过。

## 不在范围内

本轮不实现产品，不实际调用外部模型、采集或部署，不承诺工期。仅规划到现有文档定义的 V2；证券主数据、历史代码映射、自动 Fan-out、全文检索、自动交易、复杂 DAG、多租户与多 Agent 平台不是未来预留。

## 后续细化与风险

来源扩展名单、具体 Decision/MCP 服务协议、单 Owner 认证细节和目标环境在对应任务开工前复核；它们不影响本轮版本拆分。建议文件/测试名不代表已存在。实施授权仍需针对拟启动子任务审阅最新规划，路线图父任务不直接承接业务实现。
