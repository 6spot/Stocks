# 修复方案与边界

## 领域归属

- 证据身份与解析批次：docs/data.md。
- Run 重试与冻结输入：docs/execution.md、docs/research.md。
- 补证合并、Fact/来源冲突：docs/research.md、docs/data.md。
- 报告比较与控制台行为：docs/interface.md。

审查记录保存触发条件和代码证据；各叶子 design.md 给出实现建议。实现若发现本计划与最新代码不同，应先更新对应叶子材料，不能为迎合旧行号保留错误路径。

## 数据流及不变量

1. Document 内容版本与已被引用的 Fact/Chunk 是历史证据身份；当前处理状态只控制新取材，不重新解释旧输入。
2. 初始 EvidencePackage 与追加 research_inputs 是两类冻结输入。运行时基于二者生成统一视图，保存的报告引用是其经过校验的子集。
3. 报告比较只读两侧已保存的实际引用与对应冻结值；不得扫描当前 Document 的全部事实补齐或把整个输入包当成引用。
4. 补证 Fact 的数值、单位、观测期、来源与引用身份必须在上述视图间完整传递；独立来源与冲突统计继续使用既有确定性逻辑，不另造比较规则。

## 子任务依赖与共享改动

硬依赖只有 F-01 → F-04：先保证被引用 Fact 不被删除，再完成比较集合与快照口径。F-03 的补证引用投影会被 F-04 使用，因此建议 F-03 先合入；该建议不是新增功能依赖，F-04 可基于现有冻结台账接口开发。

F-02、F-03 都可能修改 research/service.py 和 execution/service.py；F-01、F-04 都涉及 Fact 证据与 API 读取。不建议在同一个共享工作目录中同时编辑这些文件。并行开发应使用隔离分支/工作树，集成者审阅合并后的证据校验和冻结边界。F-05 可以独立开发。

## 父任务集成场景

建立报告 R1 使用批次 A/Fact F；同 Document 显式 facts 重处理后 F 仍可查；产生解析批次 B 后，绑定 A 的失败 Run 仍可基于 A 重试。另一 Run 采用补证 Fact G，与初始指标冲突；生成报告 R2，保留 G 的来源/单位/期间。另放入未引用材料 U，对比 R1/R2 时 U 不成为引用新增。实际引用 G 时应保留它作为两侧真实差异。

场景需拆成最小必要测试或复用子任务新增测试，不要求一个巨型端到端用例。使用可控 Provider/Tool 和真实 PostgreSQL，不依赖真实外部凭据；真实接通仍保留延期状态。

## 回退与部署

仅修改当前实现；不新增历史迁移、回填或兼容适配器。代码回退不得通过删除历史 Fact/Chunk 或重写报告实现。确有模型结构变化时同步初始化，并按项目规则在全新测试数据库验证。
